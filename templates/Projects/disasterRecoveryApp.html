Python Based Linux Server Disaster Recovery App

GitHub: https://github.com/1SUSHANT1/DisasterRecoveryApp

About

This is a project where I create a disaster recovery app that is able to bring back my servers from complete obliteration. If you are following my work, you may know that I have 2 servers in an High Availability server cluster, active-passive system. The app I build in this project will not only bring back the servers but also configure the server cluster. The app will be a hybrid-automated app. The app will largely automate what can be automated, get user input for things like APIs, keys and instruct the user to do certain tasks. It is impossible to build the app without doing so.

Plan

This project will be split into 2 phases. Phase 1 will configure the web servers, and Phase 2 will configure the server cluster. For Phase 1, to build the web server, I will take help from this guy Sushant(terrific guy btw) who has a server setup guide at: https://www.sushantadk.com/SupportingDocuments/buildingAServer.html. The app will be built using Python. I know this can come as a shock to everybody because historically, I have always used Bash for automating almost everything. The reason I am using Python is because there are many things that can go wrong in this project. I am not saying that Bash can't handle errors because I have written a whole server cluster system in Bash. In this particular case, Python is much easier because of its libraries and built-in functionality for handling files, directories, JSON, subprocesses, networking, and exceptions. The goal of this application is not simply to execute a series of commands. It needs to make decisions based on the current state of the server, validate files and directories, handle user input, detect problems, and determine whether it is safe to continue with the recovery process. Python provides a much cleaner way to implement this logic while still allowing me to interact directly with the Linux system when necessary. This is also a good opportunity for me to become more comfortable with Python while building something that I actually need.

We need to handle this gracefully. Let's make our app detect the existing directory before it runs git clone. Here is what we need to do:
  1. Iterate through all the characters in the provided repository address
  2. Construct a word letter by letter until you get to a "/"
  3. When you get to the "/", save that word and iterate again constructing a second word
  4. If you can detect another "/", the first word isn't the one we are looking for (directory name is after the last "/" in a GItHub repo link)
  5. Keep doing this until you reach end of the file. Now your saved word will look like "myProjects.git"
  6. Iterate through this word again until you find the "."
  7. Everything before the "." will be your directory name

  2. If copy is successful, I proceed to extract the file name. To do this, I convert the Path object to string object. Split it at "/" and grab the last item on the list. Then I construct the path to where the file is. Why did I do it? stay tuned.
  3. Then I run the syntax test from the subprocess. Test the main file: /etc/nginx/nginx.conf, not the standalone file we copied because the main file includes our file which will also be checked during the test.   4. If the test passes, we break
  5. If it fails, we immediately remove the file using the file path I constructed above.
  6. Then we prompt the user to enter another file.
  7. Why remove the failed file? because if a file with incorrect syntax exists on the /etc/nginx/conf.d directory, future tests will always fail. We remove the failed file immediately after we realize the syntax is wrong and save us loads of trouble in the future.

That brings us to one major concern: flush ruleset. If the new file contains flush ruleset, it will delete the existing configuration and load new rules. So the solution is obvious right? just create a backup of the existing files so that you can recover them when you need. It's the same principle but a different approach. Once you load a file, nftables parse the file and add the rules to the kernel's ruleset. However, we don't know which files those rules came from because there's no logs for it. So how do we create a backup? We extract the current rules and keep it as a backup. 
sudo nft list ruleset
This gives us all the rules that the kernel currently has. But we can't just directly forward its output to a file and call it a backup. If we do this and later apply it, the backed up rules will be added on top of the new rules. That's not what I want the backup to do. I want the backup to replace the current rules with the rules in the backup file. 2$ for anybody who can tell me how its done (not legally binding or admissible in court. Mwehehehe). The simplest solution is to add "flush ruleset" on top of the rules. So the workflow will be:
  • Create a backup file.
  • Write "flush ruleset"
  • append the current rules

Groups and permissions

The previous quick method of adding read and execute permissions to others and recursively applying "755" permissions to the whole directory was fragile was unsafe. Fragile because if the user was running the app one directory deeper, the permissions wouldn't work and "755" permissions is too open for the website root directory. So now, let's fix them by doing the following:

  • Create a group
  • Add NGINX to the group
  • Construct a path to the current working directory
  • Leave the root directory and home directory's permissions unchanged.
  • Change the owning group of all the directories that follow to the new group we just created and add execute permissions to the group so the path can be traversed.
  • When we get to the website root directory, recursively change the group to the new group and add read and execute permissions to the group so the group.

Not only is this more secure, this is the setup I use on my main server. Execute permissions to all the files may not be necessary, but the app can't distinguish which files need to be executed from the ones which don't so this is a small compromise.

As I was building the Port Forwarding Detector, I realized this: subprocess.run(["hostname","-I"] doesn't work on Alpine's BusyBox because it doesn't have the implementation for the option "-I". However, I do already have a solution:


ipaddr=subprocess.run(["ip","-4","-o","addr","show","scope","global"],
capture_output=True,
text=True).stdout.splitlines()

localIPs=[]
for line in ipaddr:
        temp = line.split("inet")[1].split("/")[0].strip()
        localIPs.append(temp)

Seems ugly but it is necessary. And it should work on Alpine. No guarantees.
