Project Log

GitHub Repository: https://github.com/DAMSlabUMBC/libraryProject

This project log documents the development of the Smart Library, a project which is part of the Smart Campus initiative at UMBC under the leadership of Dr. Roberto Yus.

Smart Library project aims to develop a smarter and more personalized library experience using IoT and real time environmental data to help students find library spaces that best suit their needs and preferences. This project includes the design and development of systems that can leverage information such as temperature, lighting, noise levels, and other environmental variables to provide intelligent recommendations and improve the students' library experience.

The team members working on this project are Sushant Adhikari, Ibrahim Syed, Muhammad Fasihuddin, and Abdu Mahgoub. This project log is written and maintained by Sushant Adhikari. References to “I” or “me” throughout the log refer to Sushant. Work performed by other team members is identified by their name.

Original Design

I have designed the system and backend architecture until the point where the backend is production-ready. Some things that aren't in my design are the installation of the nodes, and final recommendation app. Reasons being the library will have a major hand in how the nodes will be installed and because the final app is a major component which will make the delivery even smarter with caches, previous recommendations, and predictions. The original design will be taken as a guide and will not be just "adapted", so the design may be updated in every phase. The original design documents can be found here: https://github.com/1SUSHANT1/libraryApp/tree/main/OriginalDesignDocuments

Phases

These are general description of the phases. Please refer to the Original Design Documents to see the full descriptions.

Phase 1: Genesis

Phase 1 lays the overall foundation where we cover how the ESP32s will collect the data, do some edge computing, parse the data and send it to a Raspberry PI over HTTP which will then put the data in a database and run an app which can retrieve the data from the database. The deliverables and reusables from this phase are:

  • Sensor data acquisition method
  • Sampling Interval
  • Averaging methodology
  • JSON data structure
Phase 2: MQTT Integration

I designed phase 1 to use HTTP to send traffic because of my experience with HTTP, JSON, and APIs. This will allow me to lead the team through the fundamentals of how the data is generated, formatted, transmitted and received, but the final version of the system will use MQTT, so in this phase we replace the HTTP from phase 1 with MQTT. We will receive assistance from a member of Dr. Yus's office with the implementation. The knowledge gained about MQTT in this phase will be expanded by our group in the later phases. The deliverables and reusables from this phase are:

  • MQTT communication architechture
Phase 3: Scaling Up

In this phase, the architecture from the previous phases will be made scalable. The phases above will be approached with scalability in mind but this phase will test it and modify the architecture so that new nodes can be added to with minimal effort. Ideally, the effort will be as small as giving the nodes new identifiers and they will automatically be integrated in the existing communication architecture automatically as they come online. The deliverables and reusables from this phase are:

  • Multi-node scalability and node management
Phase 4: Backend Deployment

In this phase, we replace the Raspberry Pi with the designated backend server, so the nodes, instead of reporting locally to the Pi, they will be sending their data to the designated UMBC backend server which will maintain a database of the readings. The app will also be modified to pull the data from the backend server instead of the Pi. This is the final phase of the backend architecture and these components will be validated for final design in this phase:

  • Complete backend architecture and integration.
  • Sensor to backend data pipeline
  • MQTT communication with backend infrastructure
  • Database storage and retrieval
  • Multi-node backend support
  • Application to backend integration
Following phase

After Phase 4, we will move toward installing and deploying the system in the library. As I mentioned before, the library will play a significant role in determining how the sensor nodes are deployed, whether existing library resources can be used, and whether any aspects of the system need to be redesigned to meet their requirements.

The original design documents stop here because the deployment process will be developed in collaboration with the library and within the specific requirements and constraints they establish.

Cost Estimate and Phase 1 Blueprint

The original design documents also contain the cost estimate and the phase 1 blueprint. Our group estimated the number of nodes by walking around the library and locating areas where we can, and should install the nodes. Additionally, I also created phase 1 blueprint so we have a clearer objective of how to get started. Other phases do not have a blueprint because the subsequent phases will use the previous phase as a foundation.

void loop() {
  unsigned long now = millis();

  if (now - lastSampleMs >= sampleIntervalMs) {
    lastSampleMs = now;
    if (bme.performReading()) {
      temperatureWindow.add(bme.temperature + temperatureOffsetC);
    } else {
      Serial.println("BME680 reading failed");
    }
  }

  if (now - lastReportMs >= reportIntervalMs && temperatureWindow.count > 0) {
    lastReportMs = now;
    if (WiFi.status() != WL_CONNECTED) connectToWifi();
    postReading(temperatureWindow.average());
    temperatureWindow.reset();
  }
}

UPDATE

During the presentation, we came to find out that we won't be receiving any assistance with MQTT integration until after Nov 5. That means Phase 2: MQTT integration will have to be done later. Since the system is already pretty scalable, instead of committing a huge chunk of time to Phase 3: Scaling up, we have to start materializing the project while keeping it scalable. Following a meeting with the professor, the project will move forward in the following directions:
  • More readings from the environmental sensor: The temperature sensor we are using is actually an environment sensor which is capable of reading things like pressure, humidity, release of harmful gases, etc. These readings will also be recorded by the ESP32s and transmitted to the server.
  • Connections over the Internet: Until now, the connection between the ESP32 and the server were local where both devices connected to the same AP. Moving forward, the ESP32s will be configured to connect to a working WiFi and send the data to the server over the internet.
  • Relational Database for static data: Static data like floor and area number for the nodes, whether there are windows/computers in the area, and other static data will be stored in a separate database. This enables us to program all the ESP32s the same way and get the necessary attributes for the nodes from the static database. One of the advantages of this approach is that if we decide to change the location of the nodes,instead of re-programming them, we can just update the static database.
  • Web Application: We settled on developing a web app for the system rather than a mobile app. The pipeline here can be similar to the pipeline used by my website sushantadk.com: Web Server (nginx)->Application server(Gunicorn)->Web framework(Flask/Fast API)->Data.
  • User profile and privacy: The app will store user preferences using cookies which will later be used to recommend the spaces without them having to input them every time. This will be clearly disclosed on the privacy notice and the student will always reserve the right to deny the use of cookies.
