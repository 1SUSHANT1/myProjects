Project Log

GitHub Repository: https://github.com/DAMSlabUMBC/libraryProject

This project log documents the development of the Smart Library, a project which is part of the Smart Campus initiative at UMBC under the leadership of Dr. Roberto Yus.

Smart Library project aims to develop a smarter and more personalized library experience using IoT and real time environmental data to help students find library spaces that best suit their needs and preferences. This project includes the design and development of systems that can leverage information such as temperature, lighting, noise levels, and other environmental variables to provide intelligent recommendations and improve the students' library experience.

The team members working on this project are Sushant Adhikari, Ibrahim Syed, and Muhammad Fasihuddin. This project log is written and maintained by Sushant Adhikari. References to “I” or “me” throughout the log refer to Sushant. Work performed by other team members is identified by their name.

Original Design

I have designed the system and backend architecture until the point where the backend is production-ready. Some things that aren't in my design are the installation of the nodes, and final recommendation app. Reasons being the library will have a major hand in how the nodes will be installed and because the final app is a major component which will make the delivery even smarter with caches, previous recommendations, and predictions. The original design will be taken as a guide and will not be just "adapted", so the design may be updated in every phase. The original design documents can be found here: https://github.com/1SUSHANT1/libraryApp/tree/main/OriginalDesignDocuments

Phases

These are general description of the phases. Please refer to the Original Design Documents to see the full descriptions.

Phase 1: Genesis

Phase 1 lays the overall foundation where we cover how the ESP32s will collect the data, do some edge computing, parse the data and send it to a Raspberry PI over HTTP which will then put the data in a database and run an app which can retrieve the data from the database. The deliverables and reusables from this phase are:

  • Sensor data acquisition method
  • Sampling Interval
  • Averaging methodology
  • JSON data structure
Phase 2: MQTT Integration

I designed phase 1 to use HTTP to send traffic because of my experience with HTTP, JSON, and APIs. This will allow me to lead the team through the fundamentals of how the data is generated, formatted, transmitted and received, but the final version of the system will use MQTT, so in this phase we replace the HTTP from phase 1 with MQTT. We will receive assistance from a member of Dr. Yus's office with the implementation. The knowledge gained about MQTT in this phase will be expanded by our group in the later phases. The deliverables and reusables from this phase are:

  • MQTT communication architechture
Phase 3: Scaling Up

In this phase, the architecture from the previous phases will be made scalable. The phases above will be approached with scalability in mind but this phase will test it and modify the architecture so that new nodes can be added to with minimal effort. Ideally, the effort will be as small as giving the nodes new identifiers and they will automatically be integrated in the existing communication architecture automatically as they come online. The deliverables and reusables from this phase are:

  • Multi-node scalability and node management
Phase 4: Backend Deployment

In this phase, we replace the Raspberry Pi with the designated backend server, so the nodes, instead of reporting locally to the Pi, they will be sending their data to the designated UMBC backend server which will maintain a database of the readings. The app will also be modified to pull the data from the backend server instead of the Pi. This is the final phase of the backend architecture and these components will be validated for final design in this phase:

  • Complete backend architecture and integration.
  • Sensor to backend data pipeline
  • MQTT communication with backend infrastructure
  • Database storage and retrieval
  • Multi-node backend support
  • Application to backend integration
Following phase

After Phase 4, we will move toward installing and deploying the system in the library. As I mentioned before, the library will play a significant role in determining how the sensor nodes are deployed, whether existing library resources can be used, and whether any aspects of the system need to be redesigned to meet their requirements.

The original design documents stop here because the deployment process will be developed in collaboration with the library and within the specific requirements and constraints they establish.

Cost Estimate and Phase 1 Blueprint

  • Connections over the Internet: Until now, the connection between the ESP32 and the server were local where both devices connected to the same AP. Moving forward, the ESP32s will be configured to connect to a working WiFi and send the data to the server over the internet.
  • Relational Database for static data: Static data like floor and area number for the nodes, whether there are windows/computers in the area, and other static data will be stored in a separate database.   • Web Application: We settled on developing a web app for the system rather than a mobile app. The pipeline here can be similar to the pipeline used by my website sushantadk.com: Web Server (nginx)->Application server(Gunicorn)->Web framework(Flask/Fast API)->Data.
  • User profile and privacy: The app will store user preferences using cookies which will later be used to recommend the spaces without them having to input them every time. This will be clearly disclosed on the privacy notice and the student will always reserve the right to deny the use of cookies.

One of the most important properties of this Materialized table is that it can be refreshed. When it is refreshed, it runs the query again and ensures that we have fresh data again. Refreshing it needs a index, which was created as:


library=# CREATE UNIQUE INDEX unex ON library_status(node);

Then we can refresh it with:


library=# REFRESH MATERIALIZED VIEW CONCURRENTLY library_status ;
REFRESH MATERIALIZED VIEW

The command 'CONCURRENTLY' allows us to keep retreiving data while the table is being refreshed.

Refresher App

Then I created a refresher app which refreshes the materialized table once every minute. It goes like this: 


cur=conn.cursor()

while True:
#access exclusive lock gave me a problem
        # refresh the view and commit changes
        cur.execute(
        """ REFRESH MATERIALIZED VIEW CONCURRENTLY library_status"""
        )
        conn.commit()

        # print refreshed so I know when exactly it is refreshing.
        print("refreshed")
        # sleep for a minute and refresh again
        time.sleep(60)

The bigger engineering design behind this is that since each node is sending a data every minute, we can also just refresh the active table every minute. This prevents frequents merging of databases which would be computationally expensive. So, instead of refreshing the active table every time a student puts in a request, we independently handle refreshing the table ourselves in a time we see fit.

App and the recommendation engine

Here is a snippet from the earliest implementation of the recommendation engine:


cur=conn.cursor()

#ORDER:
# 1 node

# 3 sound
# 4 soundSpike

# 6 floor
# 7 macComputers

# 9 seats

def preferenceEngine(temp,sound):
	# 2 dictionaries, one to keep score and the other to store node id as key and the data as values for easy retreival
	scoreKeeper={}
	node_data={}
	# get the data in the library_status
	cur.execute(
	""" SELECT * FROM library_status ORDER BY node"""
	)

	#get all rows
	rows = cur.fetchall()
	for row in rows:
		#update node_data which is a key value pair of node and data
		node_data[row[0]]=row;

		# variable and helper variables to count matched to the preference
		tempCon=0
		soundCon=0
		score=0

		# assign numbers to helper variables
		if row[1]>20:
			tempCon=1
		elif row[1]<16:
			tempCon=2
		else:
			tempCon=3

		if row[2]>210:
			soundCon=1
		elif row[2]<180:
			soundCon=2
		else:
			soundCon=3

		# use the helper variable to calculate score
		if tempCon==int(temp):
			score+=1
		if soundCon==int(sound):
			score+=1
		# store the score for each node in the scorekeepeer
		scoreKeeper[row[0]]=score

	# sort the data in the scorekeeper by highest score first
	sorted_data=dict(sorted(scoreKeeper.items(), key=lambda ITEM: ITEM[1], reverse=True))

	# give maximum 5 recommendations. if there is less than 5 rows, stop early
	count=0
	for node,score in sorted_data.items():
		print(f"Recommendation {count+1}")
		print(f"Floor: {node_data[node][5]}, Area: {node_data[node][0]}")
		print(f"Temperature is {node_data[node][1]}, sound is {node_data[node][2]}")
		print(f"There are {node_data[node][8]} seats, and {node_data[node][11]} outlets")
		print()
		count+=1
		if count > 5:
			break

while True:
	temp=input("Enter your temperature preference. 1: HOT, 2: COLD, 3: MODERATE: ")
	sound=input("Enter your sound preference. 1: LOUD, 2: QUIET, 3: MODERATE: ")
	print()

	preferenceEngine(temp,sound)

Recommendation engine

2026 Nov 9 , 11:07. I ended up creating my own scoring system for the recommendation engine. It goes like this: assign Hot, Moderate and Cold the numbers 1,2 and 3 respectively (lively,moderate,quiet for sound) on the javascript and transmit it to the server. When we go through the materialized view, assign the same values 1,2 and 3 to the temperature and sound on the area. Then the score is calculated as follows: 


        score=score-abs((int(temp)-int(tempCon)))-abs((int(sound)-int(soundCon)))

This single line replaced the previous implementation which was more complex, used conditionals, and wasn't effective. The idea is that the difference between the desired value and the actual value can give us how far we are from the desired state. For instance, if the desired state is 1 (hot), and the actual state is also 1 (hot), 1-1=0 so we are right where we want to be. However, if the space is 2 (moderate), |1-2|=1, so we are off by 1, and if the space is 3 (cold), |1-3|=2, so we are off by 3. Greater difference will result in lower score, and it also solves the problem with the earlier implementation by gradually moving from the desired state, to state off by 1, and the state off by 2.
