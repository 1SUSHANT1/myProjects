Galaxy A57 Boot-Chain Security Research

Project status: Incomplete. Hardware Failure

About

This research is about the boot-chain security research on a network-locked, bootloader-locked Samsung Galaxy SM-A57. The goal of this project is to unlock the bootloader, or get a foreign Operating System to boot in the phone. This research takes a comprehensive approach, covering a broad area, where its other half https://www.sushantadk.com/Projects/SamsungSecPatchAnalysis.html analyses the security updates and firmware changes on the phone which can reveal potential vulnerabilities. The phone will be exclusively be worked on in download mode, rarely booted and never connected to a network to avoid getting firmware updates.

The other half

This is a brief summary of what the other project has established. Samsung security updates bulletin at: https://security.samsungmobile.com/securityUpdate.smsb is used to analyse the changes between firmware updates. The tool samloader: https://github.com/topjohnwu/samloader-rs is used to get the firmware packages directly from the Samsung servers. First two firmware were obtained from: https://samfw.com/ and later verified using hash from multiple websites, exact device identifiers, and comparing cryptographic keys. Ghidra https://github.com/nationalsecurityagency/ghidra will be used to reverse engineer the binaries.

Why do this?

As the time of this writing, this website is being served on a Redmi Note 10 pro running Alpine Linux from postmarketOS. Even though the phone is 5 years old, I have absolutely no problem with it or its computing capacity. I am, however, not completely satisfied with the operating system on it. postmarketOS did a great job of trying to turn an Android phone into a Linux phone where features like: Touchscreen, Bluetooth, NFC, Calls, SMS, Mobile data, etc all work. However, I do not need any of those features. The only things I do need are: USB Networking, Storage, WiFi, Battery, Charging, and a very few others.

The extra features wouldn't have been a problem if the things I needed had properly worked, but the operating system didn't support charging. Even though the solution was quite small, it had to be manually fixed: https://www.sushantadk.com/SupportingDocuments/fixingUSBChargingByEditingTheDeviceTree.html. Plus, there is something going on with the sensors in the phone which causes it to reboot when you move it.

So naturally, I wanted to port my own Linux into a phone, Galaxy A57 in this case. But since this phone this phone is only 5 months old, any support on it is practically non-existent. Plus, the bootloader is locked. So the project took a long detour where now I have to find a vulnerability on the boot chain, exploit it so the phone accepts foreign operating system, then attempt to port Linux on it.

Is it even worth it?

Maybe? Let's compare it to doing this project on an iPhone 17. Let's suppose I find a vulnerability caused by poor memory management on the iPhone 17 firmware and exploit it so I can run foreign OS on it. Next month, Apple will patch it and my phone is the only iPhone in the whole world which can run foreign OS. This is kind of a dead end because then I will have to port the OS on it from scratch, minimal public documentation makes things like hardware bring up very difficult, and if I do manage it, I have to spend my whole life giving myself security updates and patches, complaining, debugging, discovering vulnerabilities, etc. Not Good.

Samsung Galaxy A57, however, will likely have Linux community support because the international model of the phone does have OEM unlocking. So even though I exploit a firmware vulnerability and Samsung patches it later, no problem. I am already on the other side and there is (well, hopes and prayers) a community on the other side.

Also, if anybody saw what I did, I am deliberately leaving the BootROM, silicon, and other physical vulnerabilities out of this comparison.

Overview

This research will largely be done on the firmware because the chances of a physical vulnerability existing on the hardware is practically non-existent. When the phone gets power, the BootROM wakes up and loads the Primary Bootloader. The primary bootloader checks the digital signature of the secondary bootloader and if verified, hands the control to the SBL and goes to sleep. There might be a vulnerability on the BootROM or the PBL, how it locates and reads the SBL, how it calculates and matches the hash, but the chances of it are very small and I don't have any practical way to research on it.

So that means the research will largely start from the SBL. However, we can't directly modify the SBL because the PBL will reject it if we do. Instead, we have to look at the firmware and see if there are some bad implementations which would lead into an exploitable vulnerability.

Verification

The system is based on Public-Key Cryptography. Samsung's private key signs the firmware, and the phone's hardware verifies the signature before handing the control to the other components. The other components such as the SBL and other firmware components are expected to maintain the same level of security as the hardware did. There are other verifications, keys and hashes involved. I will not waste time to break the public key cryptography but instead, I may investigate how it is implemented, like how is the hash calculated, how is it compared, how much time passes between when it verifies the file and when it loads the file, are other CPU cores enabled, etc.

One Question

Even though firmware is different on different models the I expect the chips to be the same. Keeping in mind that the phone can be officially unlocked, I expect there is a bit in the memory which behaves roughly like: 0 = bootloader unlocked, 1 = bootloader locked. International models have the mechanism to change this bit but network locked models don't.

How is it enforced? I don't think they go back and make this bit physically unwritable just because it is a network locked model. I think that bit is still writable but we just can't write to it. Let me explain. The bit may still be writable but we can't write on it because Samsung provides a different firmware on this phone. PBL verifies the firmware, and this firmware is missing the code which can write to that bit.

What happens if you manually update the firmware and add the code which does write to the bit? Well, the signature changes so the PBL never accepts it. So let's take one step back and look at it.

A Step Back

What does PBL actually accept? Is it the matching private key or Samsung's private key? Or in other words, does the firmware have to be signed by a master key "SamsungPrivateKeyGalaxyA57" or a specific key "SamsungPrivateKeyGalaxyA57USANetworkLocked" for the same phone, but different model? I am almost certain it is the later. Which would mean that the PBL only accepts signature from its matching private key.

Now wait a minute, how could this be if the chip is same? The only way this is possible is if Samsung goes back to the factory and rebuilds the chip, burns in a new key from scratch every time a network orders phones. I tried to do some research on it with searches identical to "when a US network carrier orders a Samsung phone, do they configure the existing phones or do they go back to the factory and start building from the chip?" but looks like this info is guarded. But the information I got was pointing to: The phone hardware is already assembled. When a network puts in an order, they configure the phones and ship them.

So if the chips and the hardware are really the same, it means that same public keys are burned into all the chips, which would mean all the chips have to accept a single key. The point I am getting to is, what is stopping me from flashing a bootloader unlocked firmware into a phone that is "supposed" to have a locked bootloader? The boundary between the hardware and the firmware is between the PBL and SBL. If we can get the PBL to accept a SBL, this problem is basically solved. Now the question is whether the PBL(hardware btw) is configured to the same key across all the models.

This looks very likely and unlikely at the same time. Unlikely because if the PBL does accept any key for the phone, we should be able to flash any firmware to any phone. But this makes "bootloader lock" and "network lock" look trivial and anybody could turn locked phones into unlocked phones using the official tools and documentations. Also, likely because tailoring SoC, BootROM, and PBL just because a network order phones seem very unlikely. So now, we'll test it. I will attempt to flash Samsung SM-A576B firmware into a phone whose label says Samsung SM-A576U.

After Flash

Heimdall fully uploaded the files but received an error before the session ended. Then the phone said: SECURE CHECK FAIL: BOOTLOADER_A. I tried to reboot the phone but it didn't wake up. I tried pressing power button, didn't work, I tried booting into Download mode by pressing the volume buttons and plugging in a charger but that also didn't work. Since there are only 3 buttons and one charging port, I can say that i tried every single combination but none of them worked. However, this is not the first time a phone has died on me. After some research online, and from my previous experiences with a similar situation, I plugged the phone to a wall charger and waited 30 mins, an hour, 2 hours, 10 hours, the phone never came back. I can reasonably conclude that the phone has been hard bricked on the hardware level.

Why did this happen?

My premise was wrong twice. The chip on the US phone was not the same as the ones on the phones from Brazil. Also, I said either the phone rejects the firmware, so it won't be written, or the phone accepts it in which case, we can unlock the bootloader because it is now running the Brazilian model. But there was a third option, where Heimdall writes the file to the specified partition without any verification so when the phone tries to verify it after it has been written, it will fail and since it is already written on the partition and the phone doesn't store a backup copy, the phone will fail internally and it can't even boot into Download mode.

Samsung did this

Yep you read that correctly, Samsung did this not me. Well, that may not be entirely correct but whatever. The phone was programmed to be hard bricked if someone tried to write a different firmware on it. This was by design, and not a mistake. The phone was told "if someone tries to something nasty, DIE".

Helpful Analogy

British commander during WWII (Samsung): If someone tries to capture you(load a different firmware), you bite down on this poison capsule and kill yourself.

Special British Agents (Galaxy A57U): If someone tries to capture me, I will bite down on this poison(I'll blow some fuses and induce hard brick) and die.

The Enemy (Me): \*\*Tries to capture the agents (unlock the bootloader)\*\*, the agent bites down on the pill and dies(Blows fuses and induces hard brick)

This might not be entirely true and I can't verify it because the phone is bricked, but if we talk generally, this is basically what happened. Could Samsung had not programmed the phone this way? Absolutely! But I'm afraid this is how they maintain security of their devices in the modern world.

How did the phone know?

Coming back to my previous assumption, how did the hardware know to not accept some firmware? Is there a way Samsung can modify the chips after production? The answer is very likely yes but then again, this info seems heavily guarded and didn't show up on general searches but I'm sure I can find more details on this once I start reading documentations. Once I find a relation between a documentation and what happened to the phone, it will be updated here. I will also try to answer why the foreign firmware got written in the partition first place? Because writing first verifying later seems like recipe for a disaster where the phone has a no way to reject a firmware without getting bricked. Can it be Heimdall? I know Odin can flash zipped files by automatically figuring out the partitions itself, and safely write the files. Heimdall on the other hand is very advanced where one has to know exactly what files goes into what partition. Is it because I flashed a single file and not the complete package? I'll try to answer these questions below. Keep in mind, all these questions converge at the same place: HOW THE CUSS DID THE PHONE KNOW?

Can it be recovered?

Considering this is a $600 phone, this should've been my first question but the answer may be no. Again, I can't say it with certainty. But I do know that Samsung prevents firmware rollbacks with fuses in the SoC. Once the phone accepts a new firmware, it blows some fuses so that if you ever try to put old firmware, the blown fuses will be an evidence that the phone was once operating with a newer firmware before and the old firmware won't be accepted.

Maybe something like this happened? If so, maybe there is also a mechanism to blow the fuses if someone tries to flash a firmware from a different? In this case flashing a bootloader unlockable firmware to a phone which was supposed to be locked forever? I'd consider this more of a threat than trying to flash an old firmware. So maybe Samsung has something like "integrity fuse" which blows up when someone try to do what I did and make the chip unusable? This is the reason why I don't think the phone is unrecoverable. If a some bootloader fuses have blown, you can simply upload a bootloader with higher revision number and the phone starts operating normally again. But what if an integrity fuse has blown? how can you ever establish security on that phone?

Someone would argue that there could be some way to perform hardware recovery using JTAG device by soldering microscopic wires straight onto the motherboard, but considering the fuses that may have blown, and my inability to operate a JTAG device or pay someone to do it, that's not going to happen. Maybe a new motherboard could work but sadly, this phone isn't getting it. So there is my answer to the question: If you try to flash an international, bootloader-unlocked firmware into a US, network-locked phone, the phone will be hard bricked. The exact cause is unknown because no debugging was possible after the flash.

Conclusion

I wouldn't attribute this entirely to lack of research on my part. I couldn't find a definitive answer about what happens when we flash a different firmware on the phone. However, my original suspicion was right, if this was possible, "bootloader-locked" phones wouldn't be a thing. I had hoped that there would be a check which would reject the file before writing, or a soft brick,but the file was written first then rejected internally, leaving me without a way to recover it.

This research was cut short because of an experiment on a undocumented behavior. I will move the other project right below this one so this can serve as a standalone failed research project.

Lessons Learned

Too many lessons were learned here the hard way in this research but there is one that defeated me. The lesson is: It is difficult to make a phone 100% secure, but it is easy to get it to kill itself if tampering is detected. Or in the analogy I used earlier, It is impossible to guarantee that your soldiers won't die, but it is easy to give them poison pills and get them to kill themselves to avoid unintended circumstances.

Logic Bombs

What makes this research even more painful is that I have worked with logic bombs before, and I know how they work, how you have to move through and disarm the bomb. This research also turned out to be a logic bomb project where if you take certain steps, the bomb will explode. Normally, I would just delete the bomb and get a new one but I can't do it here without spending another $600 making it one of my very costly mistakes.

My approach was poorly evaluated

It's not everyday that you can witness me addressing this but that's what happened. My approach was: There is no way this phone is 100% secure. There is a crack in the chain, maybe it will take me 2 years, 5 years, 10 years, or my entire life, I will find that crack, exploit it and unlock the bootloader.

What wasn't my major consideration: THE PHONE CAN KILL ITSELF IF. Flashing a different firmware was not an experiment, it was a kill command. I should've figured this out before I performed the flash.

About

This project is the other half of the research https://www.sushantadk.com/Projects/A57BootChainResearch.html where I am actively trying to find a vulnerability on the boot sequence of a network-locked, bootloader-locked Samsung SM-A576U which can lead to a untrusted Operating System booting into the system. The other project is my attempt to understand the whole architecture, boot sequence, where things are verified, where transitions happen and form a hypothesis and see if that leads to anything. This one, however is going to be strictly focused on the Samsung's OTA firmware updates and understanding what changed from the last configuration. Maybe a firmware update reveals a flaw I am looking for? But firmware can be patched, so for that reason, the phone will be rarely booted and never connected to a network so it cannot receive any updates.

OTA Updates

Samsung does not provide a direct download portal on it's website where users can manually download the firmware packages. But there are ways to get around it. If you have ever used a GitHub API to do simple things like PUT and GET, it makes sense to just make a request a Samsung phone would make for an update, the servers will send you the package.

But, Samsung doesn't provide an API documentation like GitHub so you'll have figure out a way to communicate with the Samsung Servers, bypass whatever security measures they might have to protect against this, calculate decryption keys, this and that and whatnot and get the package.

We don't have to do all that ourselves because my friends(really?) at: https://github.com/topjohnwu/samloader-rs have already figured it out and we can just use their tool to get the newest updates! Yay!
